= verisimiser — Quick Start for Platform Maintainers
:toc:
:toclevels: 2

Packaging, installing, and operating verisimiser. Every command below was
checked against the repository at the time of writing; see
<<what-is-not-packaging-ready,What is not packaging-ready>> before promising
a distro package or container image.

== Runtime Dependencies

* **None** beyond libc. `verisimiser` is a single dynamically-linked-of-libc
  binary; SQLite is compiled in via `rusqlite`'s `bundled` feature, so there
  is no `libsqlite3` runtime dependency.
* **Build-time only:** a C compiler (for the bundled SQLite) and `git` (the
  build script stamps the SHA from `HEAD`; if git is absent it records
  `unknown` rather than failing).
* PostgreSQL and MongoDB are separate servers addressed by their own
  protocols and connection strings.
* SQLite is an embedded, file-based database; its library is bundled as
  described above. In `[database]`, use `backend = "sqlite"` and set the
  environment variable named by `connection-string-env` (default
  `DATABASE_URL`) to a file path such as `/srv/myapp/app.db`. The legacy
  `connection-string` field can hold the path directly. These target
  connection settings are parsed but the CLI does not yet open the target
  database from them.

== Build from Source

[source,bash]
----
git clone https://github.com/hyperpolymath/verisimiser.git
cd verisimiser
cargo build --release        # or: just build
----

Output binary: `target/release/verisimiser` on Unix, or
`target/release/verisimiser.exe` on Windows MSVC.

Verify the build is what you packaged. On Unix:

[source,bash]
----
./target/release/verisimiser --version
./target/release/verisimiser version --json
----

On Windows MSVC (PowerShell):

[source,powershell]
----
.\target\release\verisimiser.exe --version
.\target\release\verisimiser.exe version --json
----

`version --json` emits `version`, `git_sha`, `git_describe`, and
`build_date`, baked in at compile time by `build.rs`.

== Packaging

=== Cargo (upstream-native)

[source,bash]
----
cargo install --path .
cargo install --path . --root /opt/verisimiser     # Unix example: /opt/verisimiser/bin/verisimiser
cargo install --path . --locked                    # honour Cargo.lock
----

`cargo install` places the binary at `<root>/bin/verisimiser` on Unix or
`<root>/bin/verisimiser.exe` on Windows MSVC (default root `$HOME/.cargo`
on Unix, `%USERPROFILE%\.cargo` on Windows). There is **no `--prefix` flag**
and no data, man page, or `.desktop` file to install — the old
`just install --prefix=…` examples in this repo's templates never worked.
Use `--root`.

=== Guix (experimental)

`guix.scm` describes a **development shell**, not a package:

[source,bash]
----
guix shell -D -f guix.scm
----

It pins `version = "0.1.0"` while `Cargo.toml` is at 0.2.0, so do not use it
as the basis of a distro package without updating it first. A real Guix
package would need `cargo-build-system` and a vendored/`cargo-crates`
source, which does not exist here yet.

=== Nix

There is **no `flake.nix`** in this repository. ADR-0009 keeps Nix/Guix in
the tree as experimental; only `cargo` (dev) and the Containerfile (ops,
aspirational) are named canonical.

=== Container (not ready)

The `Containerfile` is an unfilled RSR template: build steps, artifact copy,
and `ENTRYPOINT` are commented-out `TODO`s, and the header still contains
unreplaced template metadata (project name, author, year). `podman build` therefore
produces an empty image. Sealing and publishing should wait until it is
implemented (chainguard `wolfi-base` builder → `static` runtime,
`COPY --from=build /build/target/release/verisimiser /usr/local/bin/`).

=== Manual package

The complete file list to install is:

[cols="1,2",options="header"]
|===
| Path | Contents

| `$PREFIX/bin/verisimiser` (Unix) or `$PREFIX/bin/verisimiser.exe` (Windows MSVC) | The CLI binary
|===

No configuration file is installed: verisimiser has **no global config and
no XDG lookup**. Every invocation reads a `verisimiser.toml` from the path
given by `--manifest`/`-m`, defaulting to `./verisimiser.toml` in the working
directory. That makes per-user and multi-tenant installs trivial — see
<<multiple-instances,Multiple instances>>.

== Release Artifacts

`.github/workflows/release.yml` triggers on any `v*` tag and builds archives
for `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`,
`aarch64-apple-darwin`, and `x86_64-pc-windows-msvc`, each with a `.sha256`
companion, then publishes them with SLSA provenance attestations.

**No release or tag exists yet**, so there is nothing to download: the source
build is currently the only supported install path. The first tagged release
will make the archives available.

== Operating

=== Verify a deployment

[source,bash]
----
verisimiser version --json                       # binary identity
verisimiser -m /etc/myapp/verisimiser.toml validate
verisimiser -m /etc/myapp/verisimiser.toml status --json
verisimiser doctor -m /etc/myapp/verisimiser.toml
----

`status --json` is a documented, stable schema (`name`, `backend`,
`sidecar_path`, `sidecar_storage`, `octad`) — safe to scrape from your
monitoring.

=== Retention / garbage collection

[source,bash]
----
verisimiser -m verisimiser.toml gc --dry-run --json   # what would be deleted
verisimiser -m verisimiser.toml gc                    # apply
----

Bounds come from `[retention]` in the manifest (`provenance-days`,
`temporal-days`, `lineage-days`; `0` = keep forever). Schedule `gc`
alongside your existing backup rotation.

=== Sidecar backends

`sqlite` (default reference store), `postgres` (DDL dialect only — runtime
reads are **not** implemented and refuse explicitly), and the `json` family
(`plain`, `ld`, `ndjson`) with crash-safe writes and cross-process locking.
Pick per manifest under `[sidecar]`.

[[multiple-instances]]
=== Multiple instances

Because configuration is a path, not a global file, run several augmented
databases on one host:

[source,bash]
----
mkdir -p /etc/verisimiser/{orders,analytics}
cp verisimiser.toml /etc/verisimiser/orders/
cp verisimiser.toml /etc/verisimiser/analytics/
verisimiser -m /etc/verisimiser/orders/verisimiser.toml status
verisimiser -m /etc/verisimiser/analytics/verisimiser.toml status
----

Give each manifest its own `[sidecar].path` so the stores do not collide.
Connection strings are read from the environment variable named by
`[database].connection-string-env`, so secrets stay in your existing secret
manager rather than in the manifest.

[[what-is-not-packaging-ready]]
== What is not packaging-ready

State this plainly in any package description:

* **Tier 2 is stubs.** `[tier2]` overlay flags parse but nothing is
  generated or routed; do not advertise graph/vector/tensor/spatial
  overlays.
* **PostgreSQL is codegen-only at runtime.** `provenance`, `history`,
  `drift`, and `gc` refuse on the `postgres` sidecar backend.
* **Container and devcontainer are templates**, not usable artifacts.
* **No published releases yet**, so packagers must build from source and
  record the commit SHA they built.
* **Pre-alpha.** `Cargo.toml` says 0.2.0, APIs may move, and only the
  `status --json` field set plus the manifest keys are documented as stable.
